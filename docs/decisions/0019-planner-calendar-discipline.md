# ADR-0019: Расписание, план на день и дисциплина (Phase 7)

- Статус: Accepted
- Дата: 2026-10-08
- Дополняет: архитектура, разделы 5.7–5.8; ADR-0005 (даты экзаменов), ADR-0015 (повторения)

## Контекст

Архитектура описывает планировщик в общих словах: «свободное время = окна − события − поправка
на усталость», «приоритет учитывает вес задания, mastery, разрыв до цели», «80/20», «объективные
причины», «контрольная при пропуске темы», цвета дисциплины. Чтобы написать Phase 7, нужны
точные правила: как считается день, что такое пункт плана и когда он выполнен, сколько времени
на задачу, как делится время между предметами, что именно может менять ученик. Это правила
обучения, поэтому фиксируем их здесь. Все числа — значения по умолчанию в новом файле
`config/planner.toml`, их можно менять без изменения кода.

Ограничения текущего состояния: учебных блоков («теория → примеры → …») ещё нет (Phase 8),
пробников нет (Phase 9). Поэтому план Phase 7 состоит только из того, что уже умеет программа:
повторения, задачи на частые ошибки, тренировка слабых номеров, диагностика и контрольная.

## Решение

### 1. День ученика

Сервер живёт по UTC, а день ученика — по его часовому поясу. В профиль добавляется
`utc_offset_hours` (целое, по умолчанию +3, Москва; без перехода на летнее время, поэтому новая
зависимость `tzdata` не нужна). «Сегодня» для плана и дисциплины = дата по этому смещению.

### 2. Календарь (личные данные — только в базе, ADR-0004)

- **Шаблон недели** (`calendar_window`): окна для учёбы по дням недели, «с–до», например
  «пн 16:30–19:00». Ученик вводит сам; в репозиторий ничего не попадает.
- **События** (`calendar_event`): тип (школа, тренировка, соревнование, поездка, отдых, болезнь,
  другое), начало, конец, «мешает учёбе» (да/нет). Событие, которое мешает учёбе, вычитается из
  окон по пересечению по времени.
- **Чек-ин** (`daily_checkin`, раз в день, можно исправить): усталость 1–5 и «сколько реально
  есть минут сегодня» (необязательно).

### 3. Сколько времени на сегодня

```
окна   = сумма окон шаблона на этот день недели − пересечения с событиями «мешает учёбе»
бюджет = min(окна, «реально есть» из чек-ина, если указано) × множитель_усталости
```

Множитель усталости: 1 → 1.0, 2 → 1.0, 3 → 0.9, 4 → 0.75, 5 → 0.5. Без чек-ина — 1.0.
Если окон в шаблоне нет совсем — `default_minutes = 60` с пометкой «шаблон не заполнен».
Бюджет меньше `min_plan_minutes = 15` — плана нет («сегодня выходной»), дисциплину это не
портит.

### 4. Пункты плана

У пункта (`plan_item`) есть вид, предмет, номер задания ЕГЭ (если есть), количество задач,
минуты, «обязательный / дополнительный», статус (`PLANNED`, `DONE`, `PARTIAL`, `MISSED`,
`MOVED`, `EXCUSED`) и причина. Виды Phase 7:

| Вид | Откуда | Выполнен, когда |
|---|---|---|
| `REVIEW` | очередь повторений (ADR-0015), у которых подошёл срок | по каждой задаче из пункта есть завершённая попытка за этот день |
| `MISTAKE` | открытые паттерны ошибок, по убыванию приоритета | решено N задач на этот навык за день |
| `PRACTICE` | слабые номера ЕГЭ (см. п. 5) | решено N задач этого номера за день |
| `DIAGNOSTIC` | по предмету нет завершённой диагностики | диагностика по предмету завершена |
| `CONTROL` | ученик попросил «я это знаю» (п. 8) | контрольная завершена |

«Решено» = попытка завершена (ответ дан или «сдаюсь»), брошенные не считаются; правильность
на выполнение пункта не влияет — за качество отвечает mastery. Выполнение пересчитывается из
попыток, отдельно не отмечается (ученик не может «отметить вручную» — только решать).
Частично выполненный пункт (`PARTIAL`) засчитывается долей.

**Время на задачу** = норматив задачи (уже есть с Phase 2) × `time_factor = 1.3` (с разбором);
для задач без норматива — `default_task_minutes = 6`.

### 5. Как строится план (детерминированно, без ИИ)

1. Обязательная доля бюджета — `mandatory_share = 0.8`, остальное — дополнительные пункты.
2. Кандидаты по порядку: `DIAGNOSTIC` (если нужна) → `REVIEW` (сначала давно просроченные) →
   `MISTAKE` → `PRACTICE`. Обязательные набираются в этом порядке, пока хватает обязательной
   доли; что не влезло — переходит в дополнительные или на завтра.
3. **Приоритет номера для `PRACTICE`:**
   ```
   приоритет = макс_балл_номера × (1 − mastery_номера) × множитель_разрыва_предмета
   ```
   `mastery_номера` — средний mastery навыков номера (не изучен → 0.5 с пометкой).
   Множитель разрыва предмета = `max(0.2, 1 − прогноз_первичный / макс_первичный)`; без
   прогноза — 1.0. Прогноз пока в первичных баллах (ADR-0016), а цель 90+ — в тестовых; пока нет
   официальной таблицы перевода, честно сравнить их нельзя, поэтому разрыв считается до
   максимума, а не до цели. С таблицей перевода (Phase 9/11) формула станет «до цели».
4. **Баланс предметов:** доля времени предмета пропорциональна множителю разрыва, но не
   меньше `min_subject_share = 0.25`, если по предмету есть задачи.
5. Номер по одному пункту не больше `max_tasks_per_item = 4` задач, чтобы день был разнообразным.
6. У каждого пункта есть строка «почему»: «повторение: прошло 9 дней, срок был 3 дня назад»,
   «№13: mastery 0.31, вес 2 балла, прогноз по математике низкий».

План на день строится, когда ученик впервые открывает «План» или главную после полуночи (по его
времени), или по кнопке «Перестроить». Перестройка сохраняет выполненные пункты и пункты,
изменённые учеником. Дата экзамена — `TBD` (ADR-0005), поэтому «дни до экзамена» в приоритет
**не входят** в Phase 7; плановый горизонт как допущение появится, когда понадобится для
распределения тем (Phase 8).

### 6. Правило 80/20

Ученик может: менять порядок; переносить и удалять **дополнительные** пункты; добавлять свои
пункты (номер + число задач). Суммарно изменения не больше `user_change_share = 0.2` бюджета —
больше программа не даёт и объясняет почему. **Обязательный** пункт удалить нельзя: только
перенести на другой день с причиной (тогда он завтра снова обязательный).

### 7. Объективные причины

Пункт или весь день можно отметить «объективная причина» (болезнь, соревнование, поездка,
другое — с текстом). Тогда пункт получает `EXCUSED`, обязательные переносятся на ближайший день с
окнами, дисциплина этот день не учитывает. Если таких отметок больше `excuse_warn_count = 4` за
14 дней, в отчёте дисциплины честно пишется «часто объективные причины: N за 2 недели» —
без автоматического наказания.

### 8. «Я это знаю» — контрольная по номеру

Тема в Phase 7 = номер задания ЕГЭ по предмету (банк разбит по номерам). Контрольная: от 5 до
`control_tasks = 6` проверенных (`REVIEWED`) задач номера, которых ученик не решал последние 14
дней, режим `CONTROL` — без подсказок и без ИИ (как уже работает для `CONTROL`), с общим
таймером = сумма нормативов. Засчитана, если ≥ `control_pass_share = 0.8` задач решены верно,
самостоятельно и каждая не дольше норматива × 1.5. Тогда номер не попадает в `PRACTICE`
`control_skip_days = 21` день (повторения по нему остаются). Иначе номер остаётся в плане, а
отчёт показывает, какие задачи не получились. Задач для контрольной меньше 5 — программа честно
сообщает, что проверить номер нечем. Mastery меняется обычным путём, по попыткам контрольной.

### 9. Дисциплина

```
показатель = Σ выполненных минут обязательных пунктов / Σ минут выполнимых обязательных
             за последние 7 дней (дни без плана и EXCUSED не учитываются)
```

Цвет: GREEN ≥ 90% · YELLOW 75–89% · ORANGE 50–74% · RED < 50% **или** 3+ дня подряд, когда
выполнимый обязательный план был, а сделано 0. Сегодняшний день считается только после его
окончания (пока день идёт, показывается «сегодня: X из Y»). Каждый закрытый день сохраняется в
`discipline_day` (история, не пересчитывается задним числом). Тон — строгий и фактический:
«Выполнено 4 из 7 обязательных блоков (57%). Повторений просрочено: 12».

### 10. Где это видно

Сайт: главная (план на сегодня, чек-ин, цвет дисциплины), страница «План» (пункты, «почему»,
перенос, объективная причина, свои пункты), «Расписание» (окна недели и события), контрольная.
Кнопка «Решать» у пункта даёт следующую задачу этого пункта. CLI: `ege checkin`, `ege plan`,
`ege calendar`, `ege discipline`, `ege control`. ИИ в Phase 7 к плану не подключается
(`review_plan` — позже, по отдельному решению).

Таблицы (миграция 0008): `calendar_window`, `calendar_event`, `daily_checkin`, `daily_plan`,
`plan_item`, `discipline_day`, `control_session` (+ связь попыток контрольной); в профиль —
`utc_offset_hours`.

## Последствия

- План объясним: у каждого пункта есть «почему», все числа — в `config/planner.toml`.
- План работает без ИИ и без интернета.
- Расписание ученика — личные данные: только в базе на сервере/компьютере, в бэкапах, не в Git.
- План Phase 7 узкий (нет уроков и пробников); Phase 8 и 9 добавят виды пунктов, не меняя
  правил 80/20, причин и дисциплины.
- Коэффициенты (множители усталости, 0.8, 1.3 и т. д.) — стартовые предположения; после месяца
  использования их стоит пересмотреть по фактическим данным.

## Рассмотренные альтернативы

- **Шаблон «занятого» времени** (школа, сон, тренировки), а свободное считать остатком — точнее,
  но ученику дольше заполнять; окна для учёбы проще и дают тот же результат.
- **Часовой пояс через `zoneinfo`** — на Windows нужна зависимость `tzdata`; смещение в часах
  проще, а в России нет перехода на летнее время.
- **Ручная отметка «сделал»** — проще, но тогда план можно «закрыть», не решая; выполнение по
  попыткам честнее.
- **ИИ составляет план** — противоречит принципу «CORE решает» и не работает без ИИ.
