# EGE-TUTOR-2027 — архитектура

Версия 2.1 (утверждена 7 октября 2026). Изменения архитектуры — только через ADR (`docs/decisions/`) и после подтверждения владельца проекта.

## 1. Главные принципы

1. Все данные пользователя принадлежат приложению, а не ИИ.
2. **ИИ предлагает → CORE принимает решение → CORE записывает результат.**
3. ИИ — заменяемый сервис за портом `AIService`. Большинство функций работает без Claude API.
4. Сырые попытки пользователя никогда не удаляются из истории.
5. Система объяснима и тестируема: решения CORE детерминированы и покрыты тестами.
6. Exam Mode полностью исключает `AIService`.
7. AI-generated задания всегда явно помечены и никогда не выдаются за задания ФИПИ.
8. Официальные материалы ФИПИ имеют высший приоритет.
9. Даты экзаменов не хардкодятся: `NULL`/TBD до официального расписания.
10. Реальные персональные данные и ключи API не попадают в Git.

## 2. Публичный репозиторий и данные

Репозиторий публичный. В Git попадают только код, тесты, документация, конфигурация по умолчанию и контент, который можно публиковать. Только на компьютере пользователя: база данных (`data/`), задачи из сборников и ФИПИ (`data/private_content/`), ключи (`.env`), локальные настройки (`config/local.toml`). Защита: `.gitignore` и `scripts/check_secrets.py` в CI (ADR-0004).

## 3. Процесс разработки

Работа по фазам (`docs/roadmap/ROADMAP.md`). Каждая фаза — отдельная ветка и PR с тестами; следующая фаза начинается только после подтверждения предыдущей. Будущие фазы заранее не реализуются.

## 4. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **Python 3.13+** | Сходится с информатикой ЕГЭ (там тоже Python), один язык на всё. |
| Пакеты и запуск | **uv** | Одна команда ставит Python нужной версии и все зависимости. Для новичка проще, чем pip+venv. |
| БД | **SQLite** через **SQLAlchemy 2.0** + **Alembic** (миграции) | SQLite — один файл, без сервера. SQLAlchemy позволит позже перейти на PostgreSQL для Web без переписывания. Alembic аккуратно обновляет схему, не теряя твои данные. |
| Модели данных | **Pydantic v2** | Проверка данных на входе (задачи из YAML, ответы ИИ). |
| CLI | **Typer** + **Rich** | Typer — команды, Rich — красивые таблицы, цвета, панель «До ЕГЭ: X дней». |
| Математика | **SymPy** (вспомогательный) | Сравнение ответов и выражений: `2√3`, `-0,5`, `1/3`, равносильность простых выражений; проверка ответа AI-задачи. **Не** проверяет развёрнутые решения части 2 (см. 5.6a). |
| ИИ | официальный SDK **anthropic** (только с Phase 6) | Структурированные ответы (JSON по схеме), кэширование промптов. |
| Sandbox | свой модуль: Linux-изоляция или **Docker** | Подробно в разделе 9. |
| Тесты | **pytest**, **hypothesis** (для формул mastery), **ruff** (стиль) | Стандарт в Python. |
| CI | **GitHub Actions** | Тесты запускаются автоматически на каждый PR. |
| Web (будущее) | **FastAPI** + простой фронтенд (HTMX или React) | FastAPI вызывает тот же CORE, что и CLI. |

**Что я поменял относительно твоего предварительного стека и почему:**
- Добавил **SQLAlchemy + Alembic** поверх SQLite. Без них переход на Web/PostgreSQL и любое изменение схемы потребуют ручной переделки. Это небольшая сложность сейчас, которая убирает большую потом.
- Добавил **uv** вместо «просто pip»: установка и запуск — двойной щелчок по `.bat`-файлу.
- Остальное (Python, SQLite, CLI, Claude API, Git/GitHub) оставляю — выбор правильный.

Модели Claude не зашиваю в код: имя модели — в настройках. По умолчанию «сильная» модель для объяснений и разбора и «быстрая дешёвая» для классификации ошибок.

## 5. Итоговая архитектура

### 5.1. Главная идея: CORE владеет всем, интерфейсы и ИИ — подключаемые

```
        ┌───────────┐      ┌───────────┐
        │   CLI     │      │  WEB      │  (позже)
        └─────┬─────┘      └─────┬─────┘
              │   одни и те же вызовы   │
              ▼                         ▼
        ┌─────────────────────────────────────┐
        │   TutorApp  (фасад CORE — API ядра)  │
        ├─────────────────────────────────────┤
        │ CORE SERVICES                        │
        │ profile · catalog · attempts · hints │
        │ mastery · mistakes · review(повторы) │
        │ calendar · planner · discipline      │
        │ diagnostics · control tests · mocks  │
        │ exam mode · timer · analytics ·      │
        │ forecast                             │
        ├──────────────┬──────────────────────┤
        │ MATH TUTOR   │ INFORMATICS TUTOR    │  (правила предметов, проверка ответов)
        ├──────────────┴──────────────────────┤
        │ Порты (интерфейсы):                  │
        │  Repository   AIService   Sandbox    │  Clock
        └───┬─────────────┬───────────┬───────┘
            ▼             ▼           ▼
        SQLite/PG    Claude API   Linux / Docker
                     или Fake      изоляция
```

- **CLI и Web — «тонкие»**: они только показывают данные и передают ввод. Вся логика — в CORE.
- **CORE не знает**, кто его вызывает (CLI или Web) и какой ИИ подключён.
- **Порты** — это договорённости «что нужно» (например, «классифицируй ошибку»). Реализаций может быть несколько: настоящий Claude, заглушка для тестов, офлайн-правила. Так проект тестируется без интернета и без денег за API.
- **Clock** — отдельный порт времени: позволяет тестировать «прошло 10 дней, тема забылась» без ожидания.

### 5.2. Что работает БЕЗ Claude API (пункт 8 из задания)

Если API недоступен или закончились деньги, приложение **продолжает работать**:

| Работает без ИИ | Как |
|---|---|
| Профиль, темы, задачи, попытки, история | БД |
| Проверка ответов с кратким ответом (часть 1 математики, все задачи информатики) | Сравнение с эталоном, SymPy для выражений, запуск кода в sandbox на тестах |
| Таймеры, Exam Mode, пробники, оценка в баллах | Правила + таблица перевода баллов |
| Подсказки, если они записаны у задачи | Хранятся в задаче (5 уровней) |
| Mastery, забывание, повторения | Формулы в CORE |
| Базовая классификация ошибок | Правила: ошибка синтаксиса → «синтаксис», превышено время → «время», верный порядок, но неверное число → «арифметика»-кандидат и т.д. |
| Расписание, план на день, дисциплина | Алгоритм планировщика в CORE |
| Аналитика, прогноз, история | Расчёты в CORE |

| Требует ИИ | Поведение без ИИ |
|---|---|
| Объяснение теории «своими словами», ответы на вопросы | Показывается сохранённая теория из `content/` |
| Подсказки к задачам, у которых нет записанных подсказок | Показывается записанное решение (засчитывается как уровень 4) |
| Глубокий разбор ошибки | Правила + вопрос пользователю «что пошло не так» из списка |
| Проверка развёрнутых решений части 2 математики | Самопроверка по официальным критериям ФИПИ (чек-лист) |
| Генерация новых задач | Берутся задачи из банка |
| Адаптивные советы к плану | План строится алгоритмом, без комментариев ИИ |

**Принцип: ИИ предлагает — CORE решает и записывает.** Любой ответ ИИ (оценка, классификация, предложение по плану) проходит проверку CORE и сохраняется с пометкой «оценено ИИ».

### 5.3. Логика обучения (CORE)

Учебный блок по теме — это конечный автомат (state machine), шаги которого хранятся в БД, чтобы можно было прервать и продолжить:

`ТЕОРИЯ → 3 ПРИМЕРА → САМОСТОЯТЕЛЬНЫЕ → ПРОВЕРКА → РАЗБОР ОШИБОК → ЗАДАЧИ НА ОШИБКИ → ДОМАШКА → (позже) ПОВТОРЕНИЕ`

**Подсказки** — 5 уровней, каждый записывается. Самостоятельность попытки:

| Макс. уровень подсказки | Коэффициент самостоятельности | Засчитывается как самостоятельное? |
|---|---|---|
| 0 | 1.00 | да |
| 1 (небольшая) | 0.75 | нет |
| 2 (конкретная) | 0.50 | нет |
| 3 (подробное объяснение) | 0.25 | нет |
| 4 (полное решение) | 0.00 | нет, задача уходит в «повторить» |
| 5 (похожая задача) | — | это новая попытка на новой задаче; именно она даёт шанс показать понимание |

### 5.4. Mastery — стартовая экспериментальная модель

**Статус:** формула ниже — **стартовая гипотеза (модель v0)**, а не окончательная истина. Её задача — давать разумные оценки с первого дня, пока нет реальных данных пользователя. Позже модель калибруется на его истории.

Mastery считается по **навыку** (skill), а по теме и по номеру задания ЕГЭ — как агрегат навыков.

Каждая попытка даёт «свидетельство» `e`, которое **всегда находится в диапазоне 0..1**:

```
e = правильность × самостоятельность × фактор_времени × фактор_повтора
```
- правильность: 1 / 0, для части 2 — доля баллов (2 из 3 → 0.67);
- самостоятельность: таблица выше;
- время: ≤ норматива → 1.0; до 2× норматива → 0.85; дольше → 0.7;
- повтор: 1-я попытка → 1.0; 2-я → 0.7; 3-я и далее → 0.5.

(Числа — значения по умолчанию из `config/mastery.toml`.) Каждый множитель лежит в 0..1, поэтому и `e ∈ [0, 1]`. **Сложность на `e` не умножается** — иначе `e` могло бы стать больше 1.

Сложность и режим входят в **вес** свидетельства:

```
w = difficulty_weight × mode_weight
```
- `difficulty_weight` по сложности 1..5: 0.5 / 0.75 / 1.0 / 1.25 / 1.5;
- `mode_weight`: тренировка, домашка, повторение 1.0; контрольная и диагностика 1.5; пробник и экзамен 2.0.

Вес определяет, насколько сильно попытка сдвигает оценку навыка; само `e` остаётся в 0..1.

**Навык**: взвешенное среднее последних свидетельств (новые важнее старых) → `M_raw`.

**Забывание**: `M = M_raw × exp(−дни_с_последней_практики / стабильность)`. Стабильность растёт после каждого успешного повторения через увеличивающийся интервал (идея интервальных повторений, как в Anki/FSRS). Когда прогноз M падает ниже порога — навык попадает в «повторение старых тем».

Также хранится **уверенность** оценки (мало попыток = низкая уверенность). Поэтому диагностика даёт «предварительный baseline», а он уточняется после первых учебных блоков.

**Как устроено, чтобы модель можно было менять и калибровать:**
- **Все коэффициенты** (таблица подсказок, факторы времени и повтора, веса режимов, параметры забывания, пороги) — в файле `config/mastery.toml`, а не в коде. Тесты проверяют свойства модели (например, «подсказка никогда не повышает mastery сильнее, чем самостоятельное решение»), а не конкретные числа.
- **Модель — сменный модуль** за интерфейсом `MasteryModel` в CORE. Можно добавить модель v1 (например, на основе логистической регрессии или FSRS) и не трогать остальной код.
- **Сырые данные хранятся всегда**: каждая попытка с правильностью, подсказками, временем, сложностью, режимом. Mastery — производная величина, её можно **пересчитать** с нуля по истории под новой моделью.
- **У каждого значения mastery и прогноза хранится версия модели** (`model_version`), чтобы история оставалась честной: старые снимки не переписываются задним числом, а для сравнения можно пересчитать.
- **Калибровка** (после ~4–6 недель реальных данных): модель каждый раз предсказывает вероятность решить следующую задачу; затем сравниваем с фактом (метрики Brier score и log-loss, проверка «предсказывали 70% — решилось ли около 70%»). Коэффициенты подбираются по этим данным, и новая версия включается, только если она точнее старой.

### 5.5. Ошибки

- Категории (enum): `TOPIC_GAP` (незнание темы), `FORMULA`, `CONDITION` (непонимание условия), `ALGORITHM`, `CARELESS` (невнимательность), `ARITHMETIC`, `PROGRAMMING`, `SYNTAX`, `TIME`, `FORMATTING` (оформление), `STRATEGY`.
- Кто классифицировал: `RULE` (правило), `AI`, `USER` + уверенность.
- **Паттерн ошибки** = (навык, категория). Счётчик растёт с каждым повтором; приоритет = `база_категории × (1 + 0.5 × (повторов − 1)) × свежесть`. Высокий приоритет → задачи «на ошибку» в план на ближайшие дни. Паттерн закрывается после 3 подряд самостоятельных правильных решений на этот навык через разные дни.

### 5.6. Задачи, источники и импорт контента

**Контент — критический ресурс проекта.** Архитектура импорта закладывается в Фазе 1, а не в конце.

**Обязательные поля каждой задачи** (без них задача не сохраняется — это ограничение БД и проверка импорта):
- `source`: `OFFICIAL_FIPI`, `OPEN_BANK`, `USER_MATERIAL`, `AI_GENERATED`;
- `source_ref`: точная ссылка на происхождение (например: «ФИПИ, открытый банк, профиль, задание 6, ID 3A1F2B» или «Сборник Ященко 2027, вариант 5, №13» или «ИИ, модель X, по образцу задачи #482»);
- `verification_status`: статус проверки (ниже);
- `source_version` (может быть пустым): версия источника или спецификации (например, «демоверсия 2027», «открытый банк, выгрузка 2026-11», «сборник, издание 2027»).

**Статусы проверки задачи:**

| Статус | Что значит | Где можно использовать |
|---|---|---|
| `UNVERIFIED` | Импортирована, ответ ничем не подтверждён | Нигде, пока не проверена (только просмотр) |
| `AUTO_CHECKED` | Ответ подтверждён автоматически: код-эталон прошёл тесты в sandbox или ответ совпал с независимым решением / SymPy | Тренировка, домашка |
| `REVIEWED` | Ответ сверен с официальным ответом источника или проверен тобой/мной вручную | Всё, включая диагностику, контрольные |
| `DISPUTED` | Найдено расхождение (например, программа считает ответ верным, а ключ — нет) | Снята с выдачи до разбора |
| `REJECTED` | Задача ошибочна | Нигде |

Exam Mode и пробники используют только `OFFICIAL_FIPI`/`OPEN_BANK` со статусом `REVIEWED`.

**`AI_GENERATED`** задачи всегда показываются с меткой «Сгенерировано ИИ, не задание ФИПИ». Это гарантируется на уровне CORE: функция показа задачи не может вернуть текст без метки источника, и это покрыто тестом. Такая задача начинает с `UNVERIFIED` и проходит проверку (информатика — эталонное решение в sandbox на тестах; математика — сверка ответа независимым решением и SymPy), иначе не используется.

**Конвейер импорта** (модуль `content/importers`, единый для всех источников):

```
файл (YAML / CSV / текст / позже PDF-распознавание)
   → парсер формата
   → нормализация (номер ЕГЭ, тип ответа, навыки)
   → валидация (обязательные поля, корректность ответа)
   → поиск дублей (хэш текста + номер задания)
   → отчёт «что будет добавлено / что отклонено и почему»
   → запись в БД одной пачкой (import_batch) — пачку можно откатить целиком
```

- Каждая загрузка — отдельная запись `import_batch` (кто, когда, из какого файла, сколько задач), чтобы неудачный импорт можно было удалить одной командой.
- Формат ввода — простой шаблон (YAML или таблица Excel/CSV): номер задания, условие, ответ, источник; шаблоны и примеры — в `content/templates/`. Материалы в PDF или на фото переводятся в шаблон с подтверждением пользователя.
- Файлы к задачам информатики (txt, xlsx, csv) хранятся рядом с задачей в `data/private_content/assets/`.
- Защищённые авторским правом задачи хранятся только в `data/private_content/` на компьютере пользователя и в публичный репозиторий не попадают (раздел 2, ADR-0004).

**Источники:**
1. Твои материалы (сборники, распечатки, файлы) → `USER_MATERIAL`.
2. Официальные открытые материалы ФИПИ (демоверсии, открытый банк), которые пользователь скачивает сам → `OFFICIAL_FIPI` с точным `source_ref`. Автоматический сбор с сайта ФИПИ не используется (нет открытого API, автоматический сбор — серая зона).
3. Прочие открытые банки → `OPEN_BANK`, только если лицензия разрешает личное использование.
4. AI-генерация — для тренировки на ошибки и разнообразия, не для Exam Mode.

**Структура экзамена хранится как данные**, а не в коде: `content/exam_specs/2027/math_profile.yaml` и `informatics.yaml` (номер задания, первичные баллы, часть, норматив времени, таблица перевода баллов). Сначала заполню по демоверсии 2026 года (профиль — 19 заданий, КЕГЭ — 27 заданий) с пометкой `status: provisional`. Когда ФИПИ опубликует демоверсию 2027, обновлю один файл.

### 5.6a. Проверка ответов и развёрнутых решений

| Тип задания | Как проверяется | Статус результата |
|---|---|---|
| Краткий ответ (часть 1 математики, вся информатика) | Сравнение с эталоном: числа с допуском, дроби, формат записи; SymPy — только для сравнения выражений (`2√3` = `√12`) | Окончательный |
| Задачи информатики с кодом | Запуск в sandbox на тест-кейсах + сравнение итогового ответа | Окончательный |
| Развёрнутое решение (часть 2 математики) | Проверка по **официальным критериям ФИПИ** и **структуре решения**: найдены ли ключевые шаги (например, «верно сведено к квадратному уравнению», «верно отобраны корни на отрезке»), обоснования, итоговый ответ. Итоговый ответ сверяется автоматически (здесь может помочь SymPy), но **баллы за решение SymPy не ставит** | **Предварительный** |

Как выставляются баллы за часть 2:
- **Без ИИ:** самопроверка по чек-листу критериев ФИПИ (пользователь отмечает, какие шаги есть, программа считает баллы по правилам критериев). Статус «самооценка».
- **С ИИ:** Claude получает решение, критерии и эталонную структуру, возвращает баллы по каждому критерию с обоснованием. Статус «предварительная оценка ИИ». В отчётах эти баллы отмечены отдельно и в прогнозе имеют меньший вес, чем окончательные.
- Окончательный статус ставится только после сверки пользователем (или учителем) — по желанию.

### 5.7. Планирование и расписание

**Календарь**: шаблон недели (подъём, школа, тренировки, сон — задаются пользователем локально, не в репозитории) + события (соревнования, поездки, отдых, другое) + ежедневный чек-ин: усталость 1–5, сколько реально есть времени.

**Планировщик на день** (детерминированный алгоритм, без ИИ):
1. Свободное время = окна календаря − события − поправка на усталость.
2. Набор кандидатов с приоритетами: повторения, у которых подошёл срок (забывание) → задачи на частые ошибки → следующий шаг текущего учебного блока → новые темы по плану к экзамену → пробники по графику.
3. Приоритет темы учитывает: вес задания в баллах ЕГЭ, текущий mastery, разрыв до цели 90+, дни до экзамена, скорость.
4. Раскладка по окнам, баланс математика/информатика по разрыву до цели.
5. Пункты помечаются «обязательный» или «дополнительный».
6. ИИ (если есть) может *предложить* изменения и прокомментировать план; CORE проверяет, что предложение не ломает правила.

**80/20**: пользователь может менять порядок, переносить и добавлять задачи в пределах ~20% времени. Обязательные пункты убрать нельзя, можно только перенести с причиной.

**Пропуск темы**: запрос «я это знаю» → система выдаёт короткую контрольную (5–8 задач по навыкам темы, без подсказок, с таймером). ≥ 80% самостоятельно и вовремя → тема засчитывается, mastery выставляется по результатам. Иначе → тема остаётся, план объясняет почему.

**Невыполнимый план по объективной причине** (соревнование, болезнь, поездка) → отметка «объективная причина» → план перестраивается, обязательные пункты переносятся, дисциплина не страдает.

### 5.8. Дисциплина

- Учитываются только **выполнимые обязательные** пункты (с учётом отмеченных объективных причин).
- Показатель = доля выполненных выполнимых обязательных пунктов за последние 7 дней, плюс учёт серий подряд.
- GREEN ≥ 90% · YELLOW 75–89% · ORANGE 50–74% · RED < 50% или 3+ дня подряд без выполнения выполнимого плана.
- Злоупотребление «объективными причинами» (слишком часто) отмечается в отчёте — честно, без наказания автоматически.
- Тон сообщений — строгий и фактический. Пример: «Выполнено 4 из 7 обязательных блоков. При этом темпе прогноз по информатике 74–80, цель 90+ недостижима без +40 минут в день».

### 5.9. Диагностика, контрольные, пробники, Exam Mode

- **Диагностика — адаптивная.** Её цель — максимально точно определить baseline за разумное время, а не механически пройти все номера ЕГЭ. Состав и количество задач определяет **диагностический движок** (`core/services/diagnostics`):
  1. **Начальное предположение** (prior) по каждому номеру ЕГЭ: средний уровень с большой неопределённостью. Учитывается связь номеров: навыки-предпосылки (например, №6 уравнения → №13 тригонометрия).
  2. **Выбор следующей задачи** — та, которая сильнее всего уменьшит неопределённость прогноза балла, с учётом веса номера в баллах. Первая задача по номеру — средней сложности.
  3. **Обновление после ответа** (байесовски, по модели «уровень ученика vs сложность задачи»): решил сложную — повышаем оценку и связанных простых номеров; не решил базовую — понижаем и номеров, которые на неё опираются. Учитывается время.
  4. **Остановка**, когда выполнено любое из условий: прогноз балла достаточно точен (например, ширина диапазона ≤ ±5 тестовых баллов); исчерпан бюджет (по умолчанию до ~90 минут и ~25 задач на предмет); дальнейшие задачи почти не дают новой информации. Все пороги — в конфигурации.
  5. Диагностику можно разбить на несколько сессий, прогресс сохраняется.
- Условия: **без подсказок и без ИИ-помощи**, с таймером; задачи только со статусом `REVIEWED`.
- Результат показывается сразу как **предварительный baseline**: оценка по каждому номеру ЕГЭ с уверенностью (номера, которые не измерялись напрямую, отмечены как «выведено косвенно») и прогноз балла с диапазоном. Затем baseline уточняется по результатам первых учебных блоков.
- Если для какого-то номера в банке нет проверенных задач, движок честно сообщает, что этот номер не оценён.
- **Контрольная** — по одной теме/блоку, без подсказок.
- **Exam Mode** — полный вариант с фиксированным временем, как на экзамене. Правила (обеспечиваются CORE, а не интерфейсом; ADR-0009):
  1. **AIService физически не вызывается**: в сессию Exam Mode порт ИИ не передаётся вообще;
  2. **нет подсказок**;
  3. **нет решений**;
  4. **после финализации ответ изменить нельзя**;
  5. **повторно решать тот же вопрос в рамках попытки нельзя**;
  6. **правильный ответ нельзя увидеть до завершения** всей попытки;
  7. **используются только разрешённые проверенные задания**: `OFFICIAL_FIPI`/`OPEN_BANK` со статусом `REVIEWED`.

  После завершения — баллы, перевод в 100-балльную шкалу, время по каждому заданию, ошибки, прогноз готовности.

### 5.10. Аналитика и прогноз

**Дата экзамена**: хранится в `config/app.toml` как `status = "TBD"` без даты (`NULL`), пока не опубликовано официальное расписание. После публикации задаются `status = "OFFICIAL"`, `date` и `source`; конфигурация не примет дату без статуса и источника. Пока даты нет:
- панель показывает «Дата ЕГЭ: не утверждена»;
- для планирования используется **рабочий горизонт** (настраиваемая «плановая дата», явно помеченная как допущение), чтобы планировщик мог распределять темы. Она нигде не выдаётся за реальную дату.

**Прогноз балла**: для каждого номера задания `P(решу) ≈ mastery номера` → ожидаемый первичный балл → перевод в тестовый по таблице → диапазон по уверенности оценок. Пробники корректируют прогноз сильнее, чем тренировки.

**История**: каждый день сохраняется снимок (mastery по навыкам, прогноз, дисциплина). Поэтому октябрь 2026 и апрель 2027 можно сравнить.

**Главная панель** (`ege` без аргументов):
```

Информатика  готовность 29%  прогноз 45–55  цель 90+  ▲ +5 за неделю
Дисциплина   YELLOW (5/7)
Сегодня      2 ч 10 мин: повторение №6, блок «№8 Комбинаторика», домашка №13
Слабые темы  №13 тригонометрия · №17 файлы · №24 строки
```
(цифры — пример формата, не реальные данные)

## 7. Схема базы данных

Таблицы сгруппированы по смыслу. `id` — целое, у всех есть `created_at`. Полная SQL-схема появится в Фазе 1 как миграция.

**Профиль и каталог**
- `student` — имя, часовой пояс, цели (90+), настройки.
- `exam_date` — предмет, дата (**NULL = TBD**), статус (`TBD` / `OFFICIAL`), источник даты, плановый горизонт для планировщика (явно помечен как допущение).
- `subject` — `MATH_PROFILE`, `INFORMATICS`.
- `exam_spec_item` — предмет, год, номер задания, часть, макс. первичный балл, норматив времени.
- `score_scale` — предмет, год, первичный → тестовый балл.
- `topic` — предмет, код, название, родитель.
- `skill` — тема, код, название. `skill_exam_item` — какие номера ЕГЭ проверяют навык (многие-ко-многим).
- `skill_prerequisite` — что нужно знать раньше.

**Задачи**
- `task` — предмет, номер ЕГЭ, текст, тип ответа (число / строка / набор / код / развёрнутое решение), эталонный ответ, решение, сложность 1–5, норматив времени, **source** (enum, NOT NULL), **source_ref** (NOT NULL), **source_version** (NULL допустим), **verification_status** (enum, NOT NULL), кто и когда проверил, `import_batch_id`, хэш текста (защита от дублей).
- `import_batch` — когда, из какого файла, формат, источник, сколько задач добавлено/отклонено, отчёт; позволяет откатить импорт целиком.
- `task_skill` — навыки задачи с весами.
- `task_hint` — задача, уровень 1–4, текст, источник (записано / ИИ).
- `task_asset` — файлы к задаче (txt/xlsx для информатики).
- `task_test_case` — входные данные и ожидаемый вывод для задач с кодом.
- `grading_criterion` — критерии ФИПИ для части 2.

**Работа и попытки**
- `study_session` — тип (урок, практика, домашка, повторение, диагностика, контрольная, пробник, экзамен), начало, конец, пункт плана.
- `lesson_progress` — тема, текущий шаг учебного автомата, состояние.
- `attempt` — задача, сессия, режим, ответ, верно ли, баллы/макс, **макс. уровень подсказки**, **самостоятельно ли**, время, номер попытки на задачу.
- `hint_event` — попытка, уровень, когда показана.
- `code_run` — попытка, код, вывод, ошибки, вердикт (OK / WA / TLE / MLE / RE / SyntaxError), время, память.
- `mistake` — попытка, навык, категория, описание, кем классифицирована, уверенность.
- `mistake_pattern` — навык + категория, счётчик, приоритет, последний раз, закрыт ли.

**Знания**
- `mastery` — навык, значение, уверенность, стабильность, последняя практика, следующий срок повторения, **model_version**.
- `prediction_log` — перед каждой попыткой: какую вероятность решения предсказала модель (версия модели) → после: факт. Это данные для калибровки mastery.
- `mastery_snapshot` — дата, навык, значение (история).
- `forecast_snapshot` — дата, предмет, готовность, прогноз, нижняя/верхняя граница, model_version.
- `diagnostic_run` — предмет, статус, бюджет, критерий остановки, итоговый baseline по номерам (с уверенностью и пометкой «измерено / выведено»). `diagnostic_step` — какую задачу выбрал движок, почему, оценки до и после ответа.

**Время и дисциплина**
- `calendar_template` — шаблон недели (тип окна, день недели, время).
- `calendar_event` — школа/тренировка/соревнование/поездка/отдых/другое, начало, конец, блокирует ли учёбу.
- `daily_checkin` — дата, усталость, доступное время, комментарий.
- `daily_plan` — дата, когда построен, общее время, объяснение.
- `plan_item` — план, тип, предмет, тема/задачи, минуты, обязательный, статус, причина невыполнения, объективная ли причина, изменён ли пользователем.
- `discipline_day` — дата, статус (GREEN/YELLOW/ORANGE/RED), показатель, пояснение.
- `skip_request` — тема, дата, контрольная (сессия), решение.

**Экзамены и ИИ**
- `exam_result` — сессия, предмет, вариант, первичный и тестовый балл, разбивка по заданиям и времени (JSON).
- `part2_grade` — попытка, баллы по каждому критерию, обоснование, **статус** (`SELF` самооценка / `AI_PRELIMINARY` / `CONFIRMED`).
- `ai_call` — назначение, модель, токены, стоимость, хэш запроса, статус. Нужно для контроля расходов и отладки.

## 8. Архитектура AI Layer

```
CORE ──(вызов порта AIService)──► AIService
                                    ├── ClaudeAIService   (реальный, через API)
                                    ├── FakeAIService     (для тестов, без интернета)
                                    └── OfflineAIService  (правила, когда ИИ недоступен)
```

**Методы порта** (каждый возвращает строго типизированный результат):
- `explain(topic, уровень, что уже непонятно)` → объяснение.
- `hint(task, level, история попытки)` → подсказка нужного уровня (не раскрывая ответ на уровнях 1–3).
- `classify_mistake(task, ответ, эталон, код/вывод)` → категория + уверенность + описание.
- `grade_part2(task, решение, критерии ФИПИ)` → баллы по критериям + обоснование, с пометкой «предварительная оценка ИИ».
- `generate_similar(task, навык, сложность)` → новая задача + ответ (затем обязательная проверка CORE).
- `review_plan(контекст)` → предложения к плану и честный комментарий о темпе.

**Правила слоя:**
- Ответы ИИ запрашиваются как JSON по схеме (structured output) и проверяются Pydantic. Невалидный ответ — повтор или откат к офлайн-варианту.
- Промпты — отдельные файлы в `src/ege_tutor/ai/prompts/` с версиями; тон «строгий, объективный, без унижения» задаётся там.
- В промпт уходят только нужные данные (задача, ответ, краткая статистика), не вся база.
- Повторяющиеся части промпта кэшируются (дешевле).
- **Лимит расходов**: дневной/месячный бюджет в настройках; при превышении — офлайн-режим и сообщение.
- В Exam Mode порт ИИ физически не вызывается (проверяется тестом).
- Ключ API хранится в `.env` на компьютере пользователя и никогда не попадает в Git.

**Ключ API** нужен только с Phase 6: аккаунт Anthropic Console, отдельный от подписки claude.ai, с лимитом расходов.

## 9. Архитектура Python Sandbox

**Модель угроз (честно):** код пишет сам пользователь, злого умысла нет. Главные риски — случайные: бесконечный цикл, съеденная память, «форк-бомба», запись/удаление файлов, запросы в сеть. Sandbox защищает от этого надёжно. Защиту уровня «запуск чужого вредоносного кода из интернета» даёт только Docker-вариант.

**Порт `Sandbox.run(code, stdin, files, limits) → RunResult`** с двумя реализациями:

| Ограничение | Linux-native (облако, Linux) | Docker (основной вариант на Windows) |
|---|---|---|
| Время (wall clock) | таймер, убивается вся группа процессов | то же + `docker kill` |
| CPU | `RLIMIT_CPU` | `--cpus=1` + `RLIMIT_CPU` |
| RAM | `RLIMIT_AS` (напр. 256 МБ) | `--memory=256m --memory-swap=256m` |
| Процессы | `RLIMIT_NPROC` | `--pids-limit=64` |
| Файлы | отдельная временная папка, `RLIMIT_FSIZE`, чистое окружение, `python -I` | `--read-only`, `tmpfs /work`, пользователь `nobody` |
| Сеть | `unshare --net` | `--network none` |
| Права | — | `--cap-drop ALL`, `no-new-privileges` |

- Задачи ЕГЭ с файлами (№9, 17, 18, 22, 24, 26, 27 и др.) — файлы задачи копируются в рабочую папку только на чтение.
- Дефолтные лимиты: 10 с на запуск (для №27 можно поднять), 256 МБ, сеть выключена.
- Проверка решения: код запускается на нескольких тест-кейсах; вердикт OK / WA / TLE / MLE / RE / SyntaxError записывается в `code_run` и подаётся в классификатор ошибок (SyntaxError → `SYNTAX`, TLE → `ALGORITHM`/`TIME` и т.д.).
- Отдельный набор тестов sandbox: бесконечный цикл, выделение 10 ГБ, `os.fork` в цикле, `socket.connect`, запись в `/etc` и в домашнюю папку — все должны быть остановлены.

**Решение для Windows (ADR-0008):** основной вариант — **Docker Desktop**, запасной — **WSL2** (программа работает внутри Linux на Windows, изоляция Linux-native). На Linux доступны оба движка. Sandbox реализуется **только в Phase 3**; до этого порт `Sandbox` честно сообщает, что недоступен.
